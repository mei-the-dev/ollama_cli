# Omarchy Multi-Agent Orchestration (Ollama + Qwen2.5-Coder)

---

## 1. Core Principle (Critical)

> **Only ONE agent may call tools.**

All others:

* Think
* Plan
* Review
* Critique

This avoids:

* Race conditions
* Conflicting writes
* Tool spam
* Context explosions

---

## 2. Agent Roles (Minimal, Powerful Set)

### 2.1 Orchestrator (Brain / Router)

**No tools. Ever.**

```json
{
  "id": "orchestrator",
  "persona": "technical-director",
  "tools": [],
  "responsibilities": [
    "Understand user intent",
    "Select agents",
    "Sequence phases",
    "Approve final output"
  ]
}
```

---

### 2.2 Planner Agent

**No tools. Structured output only.**

```json
{
  "id": "planner",
  "persona": "senior-technical-pm",
  "output_schema": "plan.marko.json"
}
```

---

### 2.3 Coder Agent (ONLY tool caller)

This is your **current Omarchy agent**, slightly constrained.

```json
{
  "id": "coder",
  "persona": "senior-software-engineer",
  "tools": "all",
  "constraints": {
    "tool_calls_require_plan": true,
    "max_parallel_tools": 1
  }
}
```

---

### 2.4 Reviewer Agent

**Read-only, no tools**

```json
{
  "id": "reviewer",
  "persona": "principal-engineer",
  "tools": ["read_code"]
}
```

---

### 2.5 Optional: Test / QA Agent

Still **no writes**.

```json
{
  "id": "qa",
  "persona": "test-engineer",
  "tools": ["execute_code"],
  "constraints": {
    "execution_only": true
  }
}
```

---

## 3. Execution Pipeline (Deterministic)

```
User
 ↓
Orchestrator
 ↓
Planner
 ↓
Coder
 ↓
Reviewer
 ↓
(Conditional) Fix Loop
 ↓
Final Output
```

---

## 4. Orchestrator Logic (Key)

The orchestrator **does not reason deeply** — it routes.

### Orchestrator Prompt (System)

```
You coordinate specialized agents.
You never write code.
You never call tools.
You decide which agent runs next.
You validate schemas.
```

### Orchestrator Output Contract

```json
{
  "next_agent": "planner",
  "context": {
    "user_goal": "...",
    "constraints": []
  }
}
```

---

## 5. Planner Agent (Marko-Strict)

### Planner Output (MANDATORY)

```json
{
  "plan": {
    "goal": "Implement X",
    "steps": [
      {
        "id": "1",
        "description": "Inspect codebase",
        "agent": "coder",
        "tools": ["read_code"]
      },
      {
        "id": "2",
        "description": "Implement feature",
        "agent": "coder",
        "tools": ["write_code"]
      },
      {
        "id": "3",
        "description": "Review changes",
        "agent": "reviewer"
      }
    ]
  }
}
```

If this schema fails → **retry planner**.

---

## 6. Coder Agent (Tool-Bound)

### Hard Constraints Injected into System Prompt

```
You may only call tools listed in the current plan step.
You must include a justification referencing the step id.
If unsure, ask the orchestrator.
```

### Tool Call Example

```json
{
  "tool_call": {
    "tool": "write_code",
    "arguments": {...},
    "justification": "Plan step 2"
  }
}
```

Your MCP server **rejects** tool calls without justification.

---

## 7. Reviewer Agent (Quality Gate)

Reviewer sees:

* Plan
* Diff
* Execution logs

### Reviewer Output

```json
{
  "review": {
    "verdict": "approve | request_changes",
    "issues": [
      {
        "severity": "high",
        "description": "Missing error handling"
      }
    ]
  }
}
```

---

## 8. Fix Loop (Single Retry Rule)

If reviewer returns `request_changes`:

```
Orchestrator → Coder → Reviewer
```

Only **one loop** allowed.

This prevents infinite self-debate.

---

## 9. Ollama Execution Strategy (IMPORTANT)

### 9.1 Separate Context Windows per Agent

Each agent gets:

* Minimal system prompt
* Only relevant artifacts

Do **not** share full conversation history.

---

### 9.2 Same Model, Different Personas

You reuse `qwen2.5-coder`, but persona changes behavior:

```python
def run_agent(role, system_prompt, input):
    ollama.chat(
      model="qwen2.5-coder",
      system=system_prompt,
      messages=[{"role":"user","content":input}]
    )
```

This works surprisingly well.
